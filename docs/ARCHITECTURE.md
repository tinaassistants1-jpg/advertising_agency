# Архитектура

## Принцип

Канал ничего не знает про Claude, а Claude ничего не знает про Telegram. Между ними — `IncomingMessage` / `OutgoingMessage`. Новый мессенджер добавляется реализацией одного интерфейса, всё остальное работает без правок.

```
Telegram / WhatsApp
        │   ChannelAdapter → IncomingMessage
        ▼
     Router            — отвечать или молчать, какой персоной, команды
        │
        ▼
     Agent             — Claude + цикл вызова инструментов
        │
        ├─ Personas     — Рич / Арина: характер и правила Дома
        ├─ Tools        — память, задачи, напоминания
        └─ Store        — SQLite: история, настройки чатов, напоминания
                │
                ▼
        HouseMemory     — GitHub API → AI-Creative-OS/*.md
```

Параллельно работает `Scheduler`: раз в минуту проверяет напоминания, раз в час обходит группы через `CommunityKeeper`.

## Два вида памяти

Их важно не путать.

**Память разговора** — SQLite, локально. Последние `HISTORY_TURNS` сообщений чата. Нужна, чтобы ассистент понимал ход беседы. Стирается командой `/reset`, теряется при потере тома.

**Память Дома** — markdown в репозитории AI-Creative-OS. Каноны, журнал, идеи, задачи. Переживает всё; каждая запись — коммит с автором и датой. Это и есть долговременная память, о которой говорит README AI-Creative-OS.

Ассистент читает память Дома в каждый системный промпт (срез `canon.md` + хвост `journal.md`) и дописывает в неё через инструменты.

## Цикл ответа

1. Канал превращает событие в `IncomingMessage` (включая скачанные картинки в base64).
2. `Router` регистрирует чат, пишет сообщение в историю и решает: адресовано ли это ассистенту. В группе — только по имени, `@упоминанию` или ответу на его сообщение.
3. `Agent` собирает запрос: стабильная часть системного промпта (персона + канон Дома) помечена `cache_control` и кэшируется, изменчивая (время, тип чата, разовая инструкция) идёт после неё.
4. Если модель вызвала инструменты — все результаты возвращаются **одним** сообщением, цикл повторяется (не более 8 итераций).
5. Текст ответа пишется в историю и уходит в канал, длинные ответы режутся по абзацам.

## Решения и их причины

**SQLite, а не Postgres.** Один процесс, десятки чатов, никакой конкурентной записи из нескольких инстансов. Postgres здесь — лишняя инфраструктура.

**Ручной цикл tool use, а не beta-хелпер `toolRunner`.** Нужен контроль над каждой итерацией: логирование вызовов, счётчик итераций, единый формат ошибок инструмента. И одной beta-зависимостью меньше.

**Память Дома через GitHub API, а не через локальный клон.** Ассистент — не единственный, кто пишет в AI-Creative-OS: там же работают Тина и GPT. Чтение свежей версии перед каждой записью и запись по `sha` не дают перетереть чужие правки.

**Кэш чтения памяти — 5 минут.** Каждый ответ иначе стоил бы нескольких запросов к GitHub. Перед записью кэш сбрасывается принудительно.

**В группе молчание — поведение по умолчанию.** Бот, комментирующий каждую реплику, убивает чат быстрее, чем тишина.

**Арина может отказаться писать.** Инструкция оживления разрешает ответить `ПРОПУСК`. Пустой пост ради активности хуже, чем его отсутствие.

**Персона хранится в базе, а не в конфиге.** Чаты добавляются на ходу; перезапускать процесс ради нового чата не нужно.

## Что стоит знать при доработке

- **Долгий ответ.** Claude отвечает секунды; `indicateTyping` показывает «печатает…» один раз. Для очень длинных ответов имеет смысл повторять сигнал по таймеру.
- **Гонка при записи в память.** Если два чата одновременно пишут в один файл, второй получит ошибку `sha` от GitHub. Сейчас это отдаётся ошибкой инструмента, и модель может повторить. При росте нагрузки — добавить очередь на файл.
- **Лимиты Telegram.** Сообщение — 4096 символов (режется), фото — до 20 МБ (в модель уходит до 5 МБ).
- **Один процесс.** Планировщик и long polling живут в нём же. Два инстанса на одном токене конфликтуют — Telegram отдаст `409 Conflict`.
